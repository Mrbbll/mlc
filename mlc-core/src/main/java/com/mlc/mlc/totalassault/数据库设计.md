# 总力战数据库设计

本文件定义数据含义和事务；同目录的 `数据库设计.sql` 是 SQLite 建表草案。设计尚未接入插件，也不会自动创建或迁移数据库。数据库放在插件数据目录 `totalassault/totalassault.db`。

## 已确认的规则

- 每期从配置的开始时刻起固定持续 7 天，结束时刻不含在活动内；配置解析时使用 `Asia/Shanghai`。开始和结束确定后写入 `ta_activity`，不要在活动中修改其含义。若需要修改活动或难度顺序，应建立新活动 ID。
- 每位玩家一张票对应一次挑战，挑战拥有独立世界；开始前复制源区域从世界最低到最高高度的方块，挑战结束后删除世界。世界复制和文件删除属于数据库外操作，必须记录中间状态并支持重试。
- 每天北京时间 04:00 重新获得 3 张票，不累积。日期按 `instant.atZone(Asia/Shanghai).minusHours(4).toLocalDate()` 计算。活动是否开放由服务层先检查，不能仅凭票表判断。
- 玩家同时最多一个未结束挑战。挑战期间可多次出战；重启时回退正在进行的出战，票的一小时期限继续流逝。

## 数据结构

所有 UUID 统一存标准小写字符串，时间使用 UTC Unix 毫秒；`ticket_day` 使用 `yyyy-MM-dd`。所有数据库连接均须启用 `PRAGMA foreign_keys=ON`。事务使用单连接执行，写入竞争应串行化或使用 `BEGIN IMMEDIATE`；不要在事务中进行世界复制、网络请求等耗时操作。

| 表 | 内容 |
| --- | --- |
| `ta_activity` | 活动 ID、Boss ID、起止时间；起止时间在活动创建时固定。 |
| `ta_difficulty` | 每期难度的 ID 和从 0 开始的连续顺序。配置必须验证顺序唯一且连续；选择难度时以当前期已通关顺序判断。 |
| `ta_ticket_day` | 每期、每玩家、每个刷新日的剩余票数。新日首次访问时插入 3；不修改旧日记录。 |
| `ta_world_preparation` | 尚未扣票的独立世界创建记录，供重启清理孤儿世界。 |
| `ta_challenge` | 一张票的挑战、截止时间、上次保存的 Boss 血量和累计战斗时间，以及独立世界清理状态。 |
| `ta_attempt` | 挑战中的一次出战。`ACTIVE` 尚未提交，`SAVED` 已保存进度，`ROLLED_BACK` 已回退。 |
| `ta_attempt_item` | 出战时每个非空允许槽位的完整物品快照及物品分类；同类物品可以在一次出战的多个槽位出现。 |
| `ta_progress` | 每位玩家每期已通关的最高难度顺序；无记录表示只解锁第 0 项。 |
| `ta_best_score` | 每位玩家每期一条最佳成绩，引用对应成功挑战；通过该挑战下的 `SAVED` 出战读取装备快照。 |
| `ta_reward_delivery` | 奖励待投递记录，以业务唯一键去重。奖励规则尚未确定，暂不创建奖励内容。 |

`item_snapshot` 应使用 Paper 支持的完整 `ItemStack` 字节序列化格式，保留数量与组件；升级服务端时需要验证旧数据兼容性。`identity_type` 为 `MODEL` 时值为完整命名空间模型 ID；否则为 `MATERIAL` 和规范化材质名。一次出战的快照即使之后物品消耗或耐久变化也不改变。进场检查历史使用物品时，只查**当前挑战**的 `SAVED` 出战，不查 `ACTIVE` 或 `ROLLED_BACK`。回退时已消耗物品不恢复。

## 状态和事务

1. **准备世界**：检查活动、难度、装备、票数及无活动挑战。在创建世界前写 `ta_world_preparation` 的 `CREATING` 记录，使用唯一世界名，保证可定位清理；然后在数据库事务外创建世界并复制区域。失败时标记 `CLEANING` 或 `ERROR`，清理后删除该准备记录，不扣票。准备中也必须阻止同一玩家并发发起；如果重启后存在准备记录，先恢复清理，不直接认为世界可用。
2. **开始挑战**：世界准备完成后，在一个写事务里重新检查活动是否开放、仍无活动挑战、难度已解锁和票数充足；按当前刷新日插入票数行（已存在则不变），以 `remaining > 0` 条件扣票并检查更新行数，插入 `PREPARING` 挑战，最后删除准备记录并提交。挑战中固定活动、难度、世界、截止时间及初始血量。事务失败则清理准备世界，不能扣票。`expires_at_ms` 为实际开始时刻加一小时，活动结束仍独立判断。
3. **进入出战**：检查挑战仍未过期、活动仍开放、装备合规；一个事务内插入 `ACTIVE` 出战与所有进场物品快照，并将挑战改为 `BATTLING`。完成实际传送和生成失败时应回退出战，并清理实体；不得留下不可恢复的活动出战。记录开始时间以支持四分钟时限。游戏世界事件与数据库事务不能原子提交，异常时按回退处理。
4. **保存出战**：主动退出、死亡或四分钟超时后，在一个事务中将该出战改为 `SAVED`，写入本次战斗时间和结束血量，并更新挑战的累计时间、血量及 `PREPARING` 状态。所有更新须以原状态为条件并检查影响行数，防止重复提交。世界实体和物品清理由服务层完成；需要针对断线、死亡、重启分别恢复现场。
5. **回退出战**：重置、越界、普通传送、断线或服务器重启时，在一个事务内将 `ACTIVE` 改为 `ROLLED_BACK`、挑战改为 `PREPARING`；已保存血量与累计时间不变。本次快照可以保留用于现场清理，但不得用于禁用和成绩。清理新获得的物品时要用该次进场快照识别原有物品，保留原有物品战斗后的耐久等变化；不能拿进场快照直接覆盖玩家背包。
6. **结束挑战**：通关时先把最后一次出战作为 `SAVED` 提交，再在同一事务内将挑战置为 `SUCCESS`、更新最高通关难度、按下述规则更新最佳成绩，并在奖励确定后写入待投递记录。到期、活动结束或主动放弃则设置 `FAILED` 和对应原因，不写通关成绩。活动或票过期检查应在结算事务前及状态变更时再次执行，避免超时后仍成功结算。结束后标记世界 `CLEANING`，事务外清理并卸载删除；成功后置为 `DELETED`，失败置为 `ERROR` 并保留供重试。
7. **重启恢复**：先处理未完成的世界准备及已结束挑战的世界清理；对未结束挑战检查活动结束和一小时截止时间，过期则炸票，未过期但处于 `BATTLING` 的出战按回退处理。玩家断线重连后送回大厅；普通传送回退时保留传送目的地。不要仅依赖玩家在线时触发过期检查。

世界准备记录只在世界准备完成并成功创建挑战的同一事务中删除。世界名必须由插件生成并验证，删除时必须确认目标属于总力战专用目录且不包含在线玩家；失败记录不可直接当作删除成功。源世界、X/Z 区域以及出生点来自配置，不由数据库猜测。方块实体、容器数据和复制期间源区域发生变化的处理需要在世界复制实现时验证。

## 成绩、奖励和查询

通关成绩比较使用固定的 `difficulty_order`：更高难度优先；同难度累计战斗时间更短优先；时间完全相同则以后一次成绩替换。更新 `ta_best_score`、解锁难度与通关状态必须在同一事务中完成。排名规则和奖励数值未确定，不在这里定义。

`reward_key` 由发奖服务根据实际奖励业务生成，并在重试时保持不变。**本库的唯一键只能防止重复创建待办，不能单独保证跨数据库或外部邮件系统恰好投递一次**：邮件服务必须提供同一业务键的幂等写入，或让邮件写入与待办状态更新共享同一数据库事务；否则崩溃发生在邮件已投递、待办尚未标记时仍可能重复，不能启用自动重试并声称已防重。

判断玩家是否有挑战：查询 `ta_challenge` 中该 UUID 且 `status IN ('PREPARING','BATTLING')` 的记录；判断是否正在出战则检查状态为 `BATTLING`。部分唯一索引保证每位玩家最多一条活动挑战；服务层仍需检查时间和活动状态。成绩快照引用挑战，因此清理旧数据时不得删除仍被最佳成绩引用的挑战和出战。

## 迁移与限制

当前 `ticketmanager` 自行创建的是旧表 `ta_tickets(player, activity, day, remaining)`，与本设计的 `ta_ticket_day` 不同。实现时应在事务中检查 `PRAGMA user_version` 和旧表是否存在，在校验活动 ID、日期和票数后复制数据并核对，再升级版本；未知或不符合约束的数据必须报告并停止迁移，不能静默丢弃。已有数据库应先备份。之后移除旧代码的自行建表和刷新逻辑，改由统一存储层操作；本设计不会自动执行这些操作。

SQLite 事务无法与 Bukkit 世界、玩家背包或其他插件的邮件系统共同原子提交。上述状态提供恢复线索，实际实现仍须覆盖故障注入、主线程操作、物品清理和世界删除验证，不能仅凭建表就认为功能完成。
