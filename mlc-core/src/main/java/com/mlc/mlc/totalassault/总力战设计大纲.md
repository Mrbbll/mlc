# 总力战玩法设计大纲

本文记录总力战的初步设计。当前阶段仅确定玩法方向和模块职责，具体数值、配置格式和外部插件接口留待后续设计。

## 一、玩法概述

- 总力战按活动期开放，每期配置 Boss、场地、难度和奖励。
- 活动期间，每名玩家每天获得三张挑战票，可使用票进入场地挑战 Boss。
- 一张票开启一次长达一小时的挑战机会；按现实时间持续倒计时，换装、离线及服务器关闭期间也计入。期间可以多次出战，直到击败 Boss 或主动放弃；到期立即结束，未击败 Boss 则炸票，即使当时正在战斗。
- 每期活动只有一个 Boss；管理员可配置按顺序排列的任意数量难度。必须通关前一难度才能选择下一难度，三张票在各难度之间共用。每期难度解锁重置，从最低难度开始。
- 场地中除 Boss 外，还会按照配置生成小怪。
- 击败 Boss 后根据难度和用时结算：难度越高、用时越少，奖励越好。
- 奖励可以通过现有邮件功能发放。

## 二、票券与挑战流程

1. 玩家查看当前活动和剩余票数，选择难度。
2. 系统检查活动状态、场地、票数以及玩家装备。
3. 使用一张票开启挑战机会，票一经消耗不返还。
4. 玩家进入地图并开始挑战时开始计时，Boss 和小怪按配置生成。
5. 玩家可以退出本次出战并保留进度，或重置本次出战并回退到上次保存的进度；机会期间可重复进入。
6. 成功击败 Boss 后立即结束本票挑战，记录难度和累计战斗时间；奖励以后确定。
7. 玩家主动放弃或挑战失败均视为炸票，本场结束，已消耗的票不退回。

每日北京时间 04:00 刷新为三张，未使用的票不累积。跨过刷新点时当前挑战继续，新的一天另外获得三张票；当前挑战结束后才能使用新票。票数由服务器持久化管理，邮件可用于通知和奖励发放。

## 三、重置与 Boss 血量

- 主动退出、死亡或单次出战超时：结束本次出战并保留进度，可更换物品后继续挑战。
- 主动重置、传送离开或断线：回退本次出战，恢复到上次出战保存的进度；未产生过保存进度时回退到挑战初始状态。
- 保存进度时一起保存 Boss 血量、累计战斗时间和本次携带物品；回退时本次出战的伤害、用时和物品记录全部不计。
- 每次出战使用过的装备在本场后续出战中禁用，玩家需要更换其他合规装备。
- 重置时清理本次出战产生的 Boss 实体、小怪及其他需要清理的临时对象，并为下一次出战准备场地。
- Boss 阶段、技能冷却和其他状态是否保留，留待结合具体 Boss 机制确定。
- 单次出战最多四分钟；死亡或超时后保留进度，允许更换物品后继续，直到一小时到期。主动放弃视为炸票。

## 四、装备检查与使用记录

- 每次出战最多携带八格物品：头盔、胸甲、护腿、靴子、主手、副手以及快捷栏从左数第 2、3 格的药品。主手使用快捷栏第 1 格，位置可以留空，每格数量不额外限制，遵循正常堆叠上限；除以上位置和系统临时操作物品外，其他背包格子必须为空。
- 每个 Boss 在配置文件中单独设置黑名单，模型和材质分别列在 `item-models`、`materials` 中：有模型的物品只检查 `item_model`，没有模型的只检查原版材质。快捷栏第 2、3 格允许任何未被黑名单禁用的物品。战斗期间允许切换快捷栏；进场检查第 1 格作为主手，不强制改变当前选中格。检查失败时一次列出全部问题。
- 同一次出战可以携带多个同模型或同材质的物品，仅禁止之前已保存出战中使用过的同类物品。
- 有 Minecraft `item_model` 数据组件的物品按该模型判断是否相同，没有该组件的物品按材质判断；使用过一种物品后，本次挑战的后续出战禁止所有同类物品。
- 物品使用状态和历史由服务端及数据库记录、检查，不在物品 PDC 写入总力战记录。重置出战时回退本次服务端使用记录；出战中已消耗的物品不恢复。
- 装备禁用范围仅限当前这一张票对应的挑战。本场成功或炸票后解除禁用，下一张票可以重新使用。
- 战斗期间禁止主动丢弃物品，不禁止获得新物品；新获得的物品不计入本次使用记录，不检查 Boss 黑名单，任何方式离开场地时都要清理。出场按进场时的模型或材质识别原有物品，并保留其战斗中产生的耐久等变化；不考虑新旧物品同类型堆叠或转交。主动退出保存进度，传送或断线回退本次出战。
- 本场使用记录应持久化，确保重启恢复和结算时能正确判断；按模型或材质识别同类物品。

## 五、计时、成绩与奖励

- 计时从玩家进入地图并开始挑战时开始；离开战斗后暂停，重新进入战斗时继续，累计各次出战的战斗时间。
- 每期只保留最高成绩，包含活动、难度、用时和每次出战进场时的完整物品快照（含原数量）；正式评分公式确定前，先按难度高低比较，同难度用时越短越高；同难度用时完全相同时，替换为后一次成绩。
- 重置回退的出战不计入最终成绩，也不保留该次出战的物品快照。
- 建议分别设计通关奖励和活动结束后的排行奖励，并防止重复结算、重复投递。
- 挑战机会到期和单次出战超时是两个独立时限：前者按现实时间计一小时，后者每次出战计四分钟。

## 六、Boss 与场地管理

### Boss

- Boss 预计使用 BetterMob 和 BetterModel 实现；现阶段暂不接入 API，具体插件版本、API 及分工在后续开发时核实。
- 开发验证阶段使用僵尸作为临时测试 Boss，保留原版 AI、攻击能力和白天燃烧，禁止自然消失、捡装备和转化为溺尸。Boss 最大血量、攻击伤害和移动速度由配置提供，后续交由 Boss 插件适配器使用。
- 测试活动设置在北京时间 2026-11-25，难度依次为 normal、hard、hardcore、ex、ins、tm、lu。测试世界和数值使用 `totalassault/test-activity.yml` 中的临时配置，大厅和出口位于该平坦世界的场地外；测试阶段不生成小怪。
- 每个 Boss 配置唯一 ID、显示名称、外部怪物标识、难度、生成位置和奖励规则。
- 通过适配层处理 Boss 的生成、识别、血量保存、恢复和清理，隔离外部插件接口。
- 将 Boss 实体与挑战场次关联，避免不同场次之间误判死亡或结算。

### 场地与小怪

- 场地配置世界、两个对角坐标、玩家出生点、Boss 出生点、小怪出生点及退出位置。边界只检查 X、Z；玩家走出边界时结束本次出战并按重置回退。
- 支持配置多个独立场地，每个场地同一时间仅允许一名玩家挑战；整张票的一小时挑战期间持续占用同一场地。所有场地共用一个普通大厅，玩家退出出战后可以在那里存取物品、换装，重新进入时再次检查；大厅不限制玩家离开，可以通过 `/ta` 继续当前挑战。挑战结束后传送到配置的公共出口。场地未分配成功时不消耗票。应记录空闲、准备、战斗、清理和故障等状态，避免重复分配。管理员使用配置文件管理活动。
- 小怪配置类型、数量、位置、波次或刷新间隔及存活上限；每次出战结束后清理，下一次出战重新生成。
- 挑战结束或重置时清理本场实体和临时效果，确认场地恢复后再投入使用。
- 主动退出或重置本次出战时立即清理本场 Boss 和小怪。战斗中死亡时保留玩家原有物品，清理战斗中新获得的物品；不指定复活后必须在哪里换装，再次进入时重新检查。
- 需要处理玩家离线、死亡、越界、异常传送及服务器重启等情况。

## 七、邮件、数据与异常恢复

- 现有邮件功能可作为奖励投递基础；建议提取可按玩家 UUID 调用的邮件服务，支持离线玩家领取。
- 持久化活动期、每日票数、挑战状态、Boss 剩余血量、装备使用记录、计时、成绩及奖励投递状态。
- 使用项目已有的 SQLite 依赖，在插件数据目录下的 `totalassault` 目录保存独立数据库。一张票的挑战期间 Boss 和难度固定，每名玩家只能同时拥有一个未结束的挑战。
- 服务器重启时，正在进行的出战回退到上次保存的进度；一小时机会继续按现实时间流逝。活动结束立即终止挑战，未击败 Boss 的挑战炸票，不记录通关成绩。断线重连后送往大厅；普通传送触发回退但保留原传送目的地。
- 玩家通过游戏内 GUI 操作挑战、查看历史成绩和每日剩余票数，使用 `/ta` 命令打开 GUI；进入场地时在快捷栏第 9 格临时发放专用操作物品，离开场地时回收，也可通过该物品操作退出与重置。活动时间按北京时间配置，例如 `2026-12-01 04:00:00`。
- 玩家在 GUI 点击放弃时不需要二次确认，立即结束并炸票。
- GUI 风格参考项目已有的 MLC 菜单。
- 结算和奖励投递应具备防重复机制；故障补票规则需要单独确定。

## 八、建议代码划分

```text
totalassault/
├── TotalAssaultService  # 初始化、关闭与服务协调
├── activity/            # 活动期与每日刷新
├── ticket/              # 票数、扣票和炸票
├── battle/              # 挑战、出战、重置、计时与结算
├── equipment/           # 物品规则、快照与服务端使用记录
├── boss/                # Boss 配置和外部插件适配
├── arena/               # 场地、小怪和清理
├── reward/              # 成绩、奖励和邮件投递
├── storage/             # 数据持久化
├── command/             # 玩家与管理员命令
└── listener/            # 玩家、战斗和实体事件
```

## 九、建议开发顺序

1. 确定剩余玩法规则、外部插件版本和接口。
2. 实现单人、单场地的票券、装备检查、战斗、重置和计时闭环。
3. 接入 Boss、小怪和场地管理，验证血量恢复及清理。
4. 完成持久化、邮件奖励、防重复结算和异常恢复。
5. 根据需求扩展排行、图形界面和多场地并行。
